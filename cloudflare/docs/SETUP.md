# Настройка Cloudflare и GitHub

Пакет подготовлен в существующем `Water-FAQ/LamPlay`. Новый репозиторий не нужен. Ниже инструкция для будущей пробной публикации; в ходе подготовки токен не создавался и Worker в аккаунт не загружался.

## 1. Cloudflare

1. В своем браузере открыть [Cloudflare Dashboard](https://dash.cloudflare.com/), войти в существующий аккаунт и подтвердить email, если требуется.
2. Открыть **Workers & Pages**. Если предлагается первоначальная настройка Workers, выбрать бесплатный Workers Free и имя поддомена workers.dev. Добавлять сайт, менять DNS/NS и покупать домен для этого пакета не нужно.
3. Найти **Account ID** выбранного аккаунта. Это не Zone ID и не API-токен. Инструкция Cloudflare: [Find account and zone IDs](https://developers.cloudflare.com/fundamentals/account/find-account-and-zone-ids/).
4. Не включать Workers Paid, дополнительные платные продукты, Browser Run, R2/KV/D1 или собственные маршруты: подготовленный пакет их не использует.

## 2. Токен публикации

Официальная схема: [Cloudflare → GitHub Actions](https://developers.cloudflare.com/workers/ci-cd/external-cicd/github-actions/).

1. Открыть **Account API tokens** выбранного аккаунта → **Create Token**. Если интерфейс предлагает создание пользовательского токена через профиль, свериться с [Create API token](https://developers.cloudflare.com/fundamentals/api/get-started/create-token/). Не использовать Global API Key.
2. Выбрать шаблон **Edit Cloudflare Workers**, дать понятное имя, например `LamPlay GitHub deploy`.
3. Ограничить ресурсы выбранным аккаунтом. Для workers.dev этому проекту не нужны права на DNS, оплату, доменные зоны, KV/R2/D1. Проверить состав шаблона и убрать права на неиспользуемые продукты; сохранить разрешения на создание/обновление Workers и необходимые чтения аккаунта. Названия в интерфейсе могут быть Workers Scripts/Edit или Workers/Editor. Для первого создания Worker права только на уже существующий отдельный Worker не подойдут.
4. Не задавать IP-фильтр на случайный текущий IP GitHub runner: адреса стандартных runners меняются.
5. Создать токен и сразу перенести его в GitHub Actions Secret. Значение показывается ограниченно; в переписку, исходники, README, архив и настройки Lampa его не помещать.

Это учетные данные для управления Worker. Они не нужны телевизорам или пользователям LamPlay. После первого создания можно сузить область токена до конкретного Worker, если это поддерживает выбранный тип токена; проверить права по [Workers authorization](https://developers.cloudflare.com/workers/authorization/workers/).

## 3. Секреты в существующем LamPlay

В GitHub открыть **Water-FAQ/LamPlay → Settings → Secrets and variables → Actions → New repository secret**.

| Имя | Значение |
|---|---|
| `CLOUDFLARE_API_TOKEN` | Созданный Cloudflare API Token |
| `CLOUDFLARE_ACCOUNT_ID` | Account ID выбранного аккаунта |

Общедоступный репозиторий не делает значения Actions Secrets публичными. Однако код workflow, которому выданы секреты, технически может использовать их: публиковать следует только проверенный код main. Проверочный workflow не получает секретов, а deploy запускается только вручную и только из main. Изменение этого workflow также требует обычного внимательного просмотра кода.

## 4. Файлы и предварительная проверка

Подготовительная ветка должна быть перенесена в main до появления кнопки ручного запуска workflow в обычном интерфейсе Actions. Развертывание из этой подготовительной ветки специально не разрешено. Перенос папки и workflow не меняет `lamplay.js`.

Проверить перед первым запуском:

- `cloudflare/wrangler.jsonc`: имя `lamplay-metadata` свободно или осознанно соответствует вашему Worker. Deploy обновит Worker с тем же именем; чужой существующий сервис этим именем заменять нельзя.
- Namespace `92201` и `92202` для rate-limit не заняты другими вашими binding с нежелательным общим счетчиком. Это выбираемые положительные целые идентификаторы, отдельные ресурсы вручную создавать не нужно.
- `ENABLED_SOURCES` пока пуст. Это нормальная первая конфигурация для проверки инфраструктуры.
- `ALLOWED_ORIGINS` перечисляет реальные origin Lampa. По умолчанию `http://lampa.mx` и `https://lampa.mx`. Плагин, скачанный с GitHub Pages, исполняется с origin страницы Lampa, а не с origin файла плагина.
- `ALLOW_ORIGINLESS=false`: приложения без Origin сейчас не разрешены. Включать `true` после проверки реального поведения приложения; строка Origin `null` от file:// отдельно запрещена.

## 5. Первая ручная публикация

1. GitHub → **Actions → Deploy LamPlay metadata Worker → Run workflow**, ветка main.
2. Сценарий устанавливает закрепленные зависимости, выполняет синтаксическую проверку, тесты и dry-run, затем вызывает официальный action Wrangler.
3. Сохранить фактический URL из результата публикации. Он будет на workers.dev; заранее выдумывать адрес по имени аккаунта не нужно.
4. Открыть `<фактический URL>/health`. Ожидается JSON с `service: lamplay-metadata`, версией пакета и пустым `enabledSources`.

В первой конфигурации запросы источников возвращают 503 `source_disabled` и не расходуют квоту внешних API. Это не ошибка установки. Для чтения /health не требуется передавать Origin или токен.

## 6. Проверка конкретного источника

Первым проверить CDNVideoHub для фильмов/сериалов. Изменить в конфигурации `ENABLED_SOURCES` на `cdnvideohub`, сохранить изменение в main и повторно вручную запустить deploy. Настройки в Git являются источником истины: последующая публикация может перезаписать ручные изменения в кабинете.

Проверить каталог и ответ со ссылками с правильным `Origin: http://lampa.mx` из тестового клиента. Прямое открытие `/v1/...` в адресной строке браузера может не отправить Origin и получить 403 `origin_required`; это ожидаемо. Для обычной проверки через браузер использовать запрос со страницы Lampa или отдельный клиент с разрешенным origin, а не расширять allowlist на все сайты.

Затем проверить:

1. Правильный тайтл и ID, переводы, серия/сезон, нулевые/неизвестные результаты.
2. Доступность каталога из сети пользователя. Проверить ответ больше 16 KiB, а не только короткий health.
3. Прямое воспроизведение полученной ссылки на ТВ; данные могут зависеть от IP и заголовков.
4. Метрики CPU, ошибки 1102/1027, 429 и число запросов в Cloudflare. Rate limit приблизительный и не гарантирует общий дневной потолок.
5. Только после этого согласованно подключать адрес Worker в новую сборку LamPlay.

AnimeLib не переводить через Worker автоматически: проверенный API уже разрешает Lampa CORS. AnimeGO/Aniboom требуют свежих ID и подтвержденного поиска. Одновременное включение всех источников не нужно.

## 7. Ошибки и откат

| Симптом | Что проверить |
|---|---|
| Actions не показывает workflow | Файл должен присутствовать в default branch; разрешены ли Actions в настройках репозитория |
| Deploy пропущен | Запуск выбран не из main |
| Ошибка API-токена/прав | Secret, Account ID, срок и область токена, Workers permissions; пароль Lampa/HDRezka здесь не участвует |
| 503 source_disabled | Источник не включен в ENABLED_SOURCES |
| 403 origin_required/origin_denied | Фактический Origin приложения, протокол HTTP/HTTPS, правильность allowlist |
| 502 upstream_denied, upstreamStatus 403 | Источник отклонил запрос Worker; это не доказательство неверного токена Cloudflare. Нет обхода защиты в этом пакете |
| 502 upstream_redirect | Upstream сменил адрес; требуется проверить новый домен и изменить фиксированный маршрут в коде |
| 502 upstream_shape_changed | API изменил структуру или вернул иной документ; не превращать в «ничего не найдено» |
| 504 upstream_timeout | Исходящий запрос/тело не завершились за 12 секунд |
| 429 rate_limited | Локальный приблизительный лимит клиента/источника. Retry-After 60, не повторять запросы циклом |
| /health работает, крупный каталог зависает | Проверить ограничения сети пользователя и ISP, затем CPU/размер ответа |
| Каталог есть, видео не идет | Проверить прямой видеопоток, IP/Referer/Origin/CORS; Worker не проксирует видео |

Для остановки исходящих запросов очистить ENABLED_SOURCES и вручную опубликовать конфигурацию. Для возврата к предыдущему коду использовать выбранный предыдущий commit/config через обычный Git-процесс или Cloudflare rollback, затем синхронизировать Git. Простое удаление GitHub-токена не выключает уже развернутый Worker.

Вход пользователя в личном браузере Cloudflare не авторизует облачный браузер ChatGPT. Для этой схемы достаточно настроенных Secrets: управление публикацией выполняется в Actions. Секреты подключенного GitHub-приложения здесь не читаются и не запрашиваются в чате.

## Дополнение: четыре существующих источника

Для отдельных тестов ENABLED_SOURCES может содержать rezka,kodik,filmix,kinotochka. Это имена источников, не токены. REZKA_ORIGIN, KODIK_API_ORIGIN, KODIK_PLAYER_ORIGIN, FILMIX_MOBILE_ORIGIN, KINOTOCHKA_ORIGIN и KINOTOCHKA_PLAYLIST_ORIGIN задаются владельцем в wrangler.jsonc; запрос клиента не может их заменить. Разрешены только HTTPS origin без credentials/порта/пути. Для внешнего .txt/.json плейлиста KinoTochka нужно сначала проверить его реальный хост и задать KINOTOCHKA_PLAYLIST_ORIGIN; произвольный URL не принимается.

Мобильный Filmix в исходнике использует HTTP. Наш маршрут не передает пользовательский токен по HTTP: для теста нужен рабочий HTTPS API, иначе остаются Filmix TV/site-маршруты и прямой путь плагина. Не смешивать секрет публикации CLOUDFLARE_API_TOKEN с личными токенами источников. Последние не нужны в GitHub/Cloudflare vars для этого stateless-пакета.
